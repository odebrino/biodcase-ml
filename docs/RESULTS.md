# Results and evidence

## Task and evaluation units

The maintained workflow classifies **annotated audio events** into seven call types using explicit features and KNN. Annotations provide event boundaries. This is an event-classification study, a narrower task than the challenge's full sound-event detection/localization task. These scores cannot be compared directly with its detection leaderboard.

The source development dataset contains `train` and `validation`. This project reserves `validation` as its holdout and performs model selection on `train`. The challenge's separate evaluation set is not used here. See the [official task description](https://biodcase.github.io/challenge2026/task2) for the distinction.

Existing filenames and schema keys such as `official_test_metrics.json` are retained for compatibility. In this project they identify the configured holdout, not an official challenge score. Synthetic runs retain these names too; their `summary.json` explicitly identifies generated data.

New KNN reports derive majority/random baseline class frequencies from the training split. Earlier report code inferred frequencies from holdout labels; that has been corrected and covered by a regression test with reversed train/holdout class balance. Historical stored scores have not been regenerated or silently changed.

## Featured stored comparison

The selected 7-class candidate in [`best_cv_metrics.json`](../outputs/reports/knn_search/best_cv_metrics.json) uses `lowfreq_all_plus_waveform_spectral`, mean imputation, standard scaling, `SelectKBest`, and a 7-neighbor uniform Minkowski KNN. The stored search limits development data to 1,000 events per class.

| Validation scheme | Accuracy, mean ± fold SD | Macro-F1, mean ± fold SD |
| --- | --- | --- |
| Stratified 4-fold | 0.7583 ± 0.0133 | 0.7583 ± 0.0132 |
| Leave-one-domain-out, 3 folds | 0.1612 ± 0.0780 | 0.1089 ± 0.0339 |

Both rows describe the **same selected configuration**, on different partitions. They illustrate sensitivity to evaluation design. This configuration was selected using stratified CV; the domain-aware result is a diagnostic, not an independently selected final performance claim. Fold SD is not a confidence interval. The three domain folds do not represent evaluation over every source deployment.

The `cv_metrics` aggregate confusion-matrix scores in the JSON differ slightly from averages over folds. The table and plot consistently use `best_candidate` mean/std fields. [Split record](../outputs/reports/knn_search/split_strategy.json), [per-candidate/domain comparison](../outputs/reports/knn_search/domain_cv_results.csv), [search configuration](../outputs/reports/knn_search/search_config_used.yaml).

Regenerate the figure from the committed JSON:

```bash
python scripts/render_portfolio_figure.py
```

This regenerates a visualization, not the underlying experiment. Re-running the experiment requires the external audio, matching source version, and the recorded configurations. Current CPU tests and the synthetic demo validate software behavior without reproducing these historical scores.

## Re-running real-data analysis

After obtaining the matching raw development data, follow [DATA_ACCESS.md](DATA_ACCESS.md). Use `python -m src.models.knn_search --help` for the maintained train-only search entry point and the stored configuration to understand the comparison. A fresh experiment should record its actual command, environment, seed, manifest hash, sampling, and split strategy in a new output directory.
